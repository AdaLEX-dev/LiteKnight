# 07 — Feature Cookbook

These recipes are the shortest honest path to common changes. Always finish with
a build and the relevant regression.

## 1. Add a runtime weapon definition

1. Recover or identify the weapon prefab in the reference tree.
2. Add/merge it into `analysis/assets/weapon_catalogue.json` (usually via
   `tools/asset/merge_canonical_weapons.py`).
3. Add it to a generated scene’s `weapons` array. The scene loader expects:
   - `id`
   - `display_name`
   - `class_name`
   - `audio_clip` (recovered; never leave blank and inherit pistol)
   - `visual_sprite`
   - `attack_cycle_seconds`, `first_shot_delay_seconds`
   - `damage`, `bullet_speed`, `size`, `critic`, `deviation`
   - `energy_cost`/`consume`
   - `projectile` (`id`, `sprite`, `prefab_speed`, `lifetime`, collider)
   - optional `special`, `muzzle_sprite`, visual curves, melee fields
4. Regenerate/copy the scene.
5. Add a unit test for the definition and at least one combat behavior.
6. Run:
   ```bash
   ./build/soul-knight-test --test-case="*weapon*"
   ./build/soul-knight --devroom --smoke-seconds 3
   ```

Do not use the Bad Pistol as a fallback for audio/projectile/muzzle. If a field
is unknown, leave it empty and document the gap.

## 2. Add a weapon special behavior

1. Check `WeaponSpecial` in `SceneAsset.hpp` and `Weapon.cpp` event handling.
2. Add the data field and parse it in `SceneLoader.cpp`.
3. Implement the event in `Weapon::Update`/`TakeFireEvents` and handle it in
   `Application::FixedUpdate` if it needs world state.
4. Add a unit test with a synthetic `WeaponDefinition`.
5. Add a devroom/review smoke if it needs rendering.

Keep per-weapon presentation changes inside `WeaponRenderer::ComputePresentation`
or data fields. Do not add offsets in `Application` draw calls.

## 3. Add an enemy

1. Recover the enemy prefab/ID and sprite/animation metadata.
2. Add it to the enemy catalogue/scene definitions.
3. Add its AI branch in `EnemySystem` or a new focused controller.
4. Add spawn weights to the biome pool if appropriate.
5. Add tests:
   - definition loads;
   - spawn;
   - damage/death;
   - contact/attack behavior;
   - room clear counts it.
6. Run the combat smoke and a room activation test.

Full EnemyAI04 pathfinding is still partial. If you implement a simplified AI,
label it as a native approximation.

## 4. Add a room or pattern

1. Add the room to the asset builder input list.
2. Recover floor/wall cells, doors, colliders, sprites, and theme.
3. Generate `analysis/assets/scenes/<room>.json` and generated pixels.
4. Copy to runtime via `prepare-assets.sh`.
5. Add it to the room catalogue/DungeonPlan/biome pools.
6. Add a geometry area test and a room activation transition test.
7. Validate:
   - all doors match entrances;
   - floor is reachable;
   - no artificial invisible walls;
   - enemy spawn points are on floor;
   - boss/special room flags are correct.

## 5. Add an interaction marker

Markers are in `SceneAsset::interaction_markers` (generated by the scene builder
or appended at runtime).

Fields:

```json
{
  "id": "unique_id",
  "kind": "npc|door|mission|weapon_chest|material_chest|weapon_station|forge|garden|trader|mech|pet|character",
  "label": "DISPLAY LABEL",
  "position": [x, y],
  "radius": 3.0,
  "speaker": "optional",
  "text": "optional",
  "text_alt": "optional",
  "talk_lines": ["..."],
  "character_id": "optional cXX"
}
```

1. Add the marker in `build_hub_scene.py` (for hub) or the room builder.
2. Handle `marker->kind` in `Application::TryInteract`.
3. Use recovered localization for dialogue.
4. Add a coordinate test that checks marker position/kind/lines.
5. Add a gameplay smoke step if it mutates state.

## 6. Add a UI screen

1. Add the enum value in `GameUI.hpp` (`UIScreen`).
2. Add draw data fields to `GameUIData`.
3. Add an open method (`OpenX`) and close/back behavior.
4. Add a draw method and dispatch in `GameUI::Draw`.
5. Add pointer hit-testing/selection handling.
6. Add `UIAction` values for confirm/cancel/mutation.
7. Handle the actions in `Application::ProcessUIAction`.
8. Add a unit test for open/close/selection and `ProcessUIAction` if possible.
9. Add a `--review-area` that opens the screen for screenshot inspection.
10. Add a CTest/QA check if the screen has invariant data.

Use recovered UI assets where available; do not build a text-only imitation of a
graphical reference screen.

## 7. Add a save field

1. Add the field to `SaveData`.
2. Write it in `SaveSerializer::Serialize`.
3. Read it in `SaveSerializer::Deserialize`, with a safe default for old saves.
4. Snapshot it in `Application::SaveGameToDisk`.
5. Restore it in `Application::LoadGameFromDisk`.
6. Add a field to `tests/unit/save_test.cpp` `MakeSave()` and assert round-trip.
7. If the field belongs to a room item, add it to `SaveChestState`/
   `SaveRoomItems` and the room restore path.
8. If compatibility matters, bump `SaveData::kCurrentVersion` and handle old
   versions.

The material/unlocked-blueprint load path was previously missing even though the
write path existed. Always test a full round-trip, not just serialization.

## 8. Add collision to a scene object

1. Identify the actual object first. Do not put a rectangle around the whole
   sprite if it is a table with legs.
2. If the reference has a small collider, use it.
3. If the sprite is furniture, derive a footprint from the visible base.
4. Add the collider in the scene builder, not in `build/assets`.
5. Add probes from left, right, top, bottom, and diagonal.
6. Add a regression that the player can approach to the intended edge and cannot
   pass through.
7. Ensure neighboring legitimate walls remain solid.

Examples:

- forge tables: per-table footprint, top at `y + 2.39`;
- object-portal long tables: sprite width + 2-unit base;
- oxygen bottles: recovered polygon AABB;
- wall cap at `(7.5,-22.5)`: removed entirely;
- stair opening: no artificial 3x3 block; thin floor edge only.

## 9. Add a new NPC / dialogue

1. Find the character/object in the reference hierarchy.
2. Recover the speaker name and dialogue terms from localization.
3. Add an `npc` marker at the correct position/radius.
4. If it is a `TalkCharNpc`, add its `character_id`; the runtime hides the
   selected player duplicate.
5. Add talk lines in order; do not invent lines when recovered terms exist.
6. Add a coordinate regression and a gameplay-smoke talk check.

## 10. Add a chest rule

1. Recover the chest prefab class and serialized fields.
2. Add/modify `ChestDefinition` in `ItemAssets`/`build_item_assets.py`.
3. Implement the loot rule in `ItemWorld::Update`.
4. Use `loot_seed_` + room id + chest index for deterministic randomness.
5. Test:
   - open time;
   - loot count;
   - multiple seeds;
   - no duplicate drops;
   - opened state across room transitions;
   - save/load.
6. For the hub, use `hub_weapon_chest`, not appointed `chest00`.

## 11. Add a trader/merchant offer

1. Use the recovered item drop table and weapon catalogue.
2. Select only weapons that exist in the current scene and have a valid price.
3. Derive stock from `trader_stock_seed_`.
4. Persist the seed and sold offer indices.
5. Test fixed seed A/B/A and purchase deduction.
6. Render three offers; world pedestals use vertical orientation and actual
   sprite pivots.

## 12. Add a blueprint/material recipe

1. Recover the recipe from `weapon_materials.json` or the reference material
   component.
2. Add it to the workshop data; never invent a cost.
3. If blueprint-gated, add the recovered `blueprint_weapon_*` ID to the lock set.
4. Ensure `CanCraft` checks blueprint + materials.
5. `ConsumeForCraft` must be atomic: no deduction on failure.
6. Test locked, insufficient, sufficient, craft, deduction, delivery,
   save/load, repeated craft.
7. UI must show locked/unlocked state and owned material counts.

## 13. Add a review area

1. Add the name to `AppConfig.cpp` review parsing so it loads the hub.
2. Add the teleport/UI branch in `Application::ConfigureReviewMode`.
3. Keep the player south of the subject for camera framing.
4. Add a screenshot to the release note if visual.
5. Add the area to the geometry probe if it has a geometric invariant.

## 14. Add a CTest/QA test

1. Prefer a Python QA script if the check needs scene JSON coordinates.
2. Add it to `CMakeLists.txt` under `if(PYTHON3_EXECUTABLE)`.
3. Use `WORKING_DIRECTORY "${CMAKE_CURRENT_SOURCE_DIR}"`.
4. Set a timeout and label (`runtime` for windowed tests).
5. Ensure it fails with a detailed report, not just a traceback.
6. Do not require the reference APK unless the test is explicitly local-only.

## 15. Commit and release

```bash
git status
git diff --stat
./build/soul-knight-test
python3 tools/qa/living_room_coordinate_regression.py
ctest --test-dir build -R "coordinate|trader|gameplay" --output-on-failure
git add <paths>
git commit -m "fix(scope): outcome"
```

For a beta release, follow `01-GIT-GITHUB-RELEASES.md`.
