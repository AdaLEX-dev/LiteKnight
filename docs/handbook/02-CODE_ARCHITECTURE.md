# 02 — Code Architecture

## 1. Mental model

LiteKnight is one native process with four broad layers:

```text
Platform  ->  Engine  ->  Game  ->  Application
SDL3/Vulkan    reusable    Soul Knight   composition, mode flow,
window/input   math,       rules, data,   scene loading, review modes,
audio/time     assets,     combat, UI     save orchestration, world graph
               collision
```

The boundaries are not enforced by separate processes or plugins. They are
enforced by discipline and include direction:

- `platform/` knows SDL, XDG paths, audio devices, and frame timing.
- `engine/` knows generic 2D runtime primitives: vectors, rectangles, collision,
  scene data, texture data, rendering, animation, RNG.
- `game/` knows Soul Knight semantics: weapons, rooms, characters, chests,
  plants, pets, saves, UI data.
- `app/` is the only composition root. `Application` owns the window, renderer,
  scene, player, UI, systems, and the main loop.

Gameplay code must not call `SDL_*` or Vulkan directly. If a game system needs a
platform service, pass data in or expose it through an engine abstraction.

## 2. Entry point

`src/app/main.cpp`:

1. initializes logging;
2. parses `AppConfig`;
3. enables validation in Debug;
4. creates `Application`;
5. calls `Application::Run()`;
6. shuts down logging.

`Application::Run()` is in `src/app/Application.cpp`. It initializes the window,
renderer, assets, scene, and game state, then loops:

```text
PollEvents()
  -> input snapshot / menu actions / review controls
accumulate frame time
  -> FixedUpdate(1/50) at 50 Hz
  -> BuildRenderBatch()
  -> UiRenderer/GameUI draw
  -> Vulkan present
```

The exact ordering is critical: gameplay state advances only in `FixedUpdate`.
Rendering interpolates positions where applicable, but never changes simulation
state.

## 3. Initialization path

`Application::Initialize()` performs, in order:

1. frame timer/window setup;
2. Vulkan renderer creation;
3. filesystem/XDG initialization;
4. audio engine initialization;
5. asset-root detection (`AssetEnvironment`);
6. UI atlas loading;
7. scene load (`SceneLoader::Load`);
8. character/weapon/obstacle/enemy configuration;
9. item assets (`ItemAssets`);
10. save manager and UI layout;
11. world/room graph or hub configuration;
12. review-mode setup when requested.

The log is intentionally verbose. Read it top-to-bottom when startup fails.

## 4. Scene model

`src/engine/assets/SceneAsset.hpp` is the central data contract. Major types:

- `TextureData` / `SpriteData`
- `SpriteInstance`
- `SceneDoor`
- `SceneCharacter` / animation IDs
- `WeaponDefinition`, `ProjectileDefinition`, `WeaponVisualKey`
- `EnemyDefinition`
- `InteractionMarker`
- `Collision` solids and floor/wall cells
- `LevelTheme` / `LevelSurfaceSprite`
- `PlayerStats`
- UI/shop/item metadata loaded into separate systems

`SceneLoader::Load()` reads generated JSON and resolves sprite IDs to indices.
Every scene must be self-contained: the runtime does not read Unity assets.

Scene JSON is generated by tools under `tools/asset/`. The runtime copy lives at
`build/assets/scenes/...`; the committed metadata copy lives under
`analysis/assets/scenes/`. Treat the generator as the source of truth.

## 5. Application composition

`Application.hpp` contains the system members. The most important ones:

| Member | Responsibility |
|--------|----------------|
| `window_` | SDL3 Wayland window and events |
| `renderer_` | Vulkan instance/device/swapchain/sprite pipeline |
| `sprite_batch_` | per-frame sprite submission |
| `frame_timer_` | fixed-step accumulator and render pacing |
| `filesystem_` | XDG paths, asset reads, saves |
| `scene_` | current loaded scene |
| `player_` | movement/collision state |
| `collision_world_` | current solids, including doors/obstacles |
| `player_characters_` | all 15 recovered heroes and active selection |
| `weapons_` / `weapon_inventory_` | weapon definitions and two slots |
| `weapon_` / `secondary_weapon_` | active combat state |
| `projectiles_` | live projectile simulation |
| `enemies_` | enemy definitions/instances/AI |
| `player_health_` / `player_energy_` | player resources |
| `item_assets_` / `item_world_` | chests, coins, item definitions |
| `workshop_` | recovered forge recipes/material inventory/blueprints |
| `plant_system_` | garden plots/seeds |
| `pet_` / `summons_` | companion/summon state |
| `game_ui_` | screen state and draw logic |
| `ui_renderer_` / `ui_assets_` | logical UI drawing and recovered atlases |
| `hud_layout_` | persistent logical HUD rects |
| `save_manager_` | versioned JSON save |
| `room_manager_` / `room_doors_` | dungeon graph and door lifecycle |
| `obstacles_` | recovered obstacle variants and collision cells |
| `asset_lab_` | developer asset browser |

`Application` is large by design because it is the game’s composition root. When
adding a system, prefer a focused class under `src/game/` and keep `Application`
responsible for wiring, input, and lifecycle only.

## 6. Fixed-step loop

`FixedUpdate(double dt)` in `Application.cpp` (around line 5783):

1. run gameplay smoke automation if enabled;
2. decrement visual/temporary timers;
3. update plant system, weapon pickups, dialogue, stake damage;
4. advance room activation state (`Entered -> Combat -> Cleared`);
5. update door animation and rebuild collision when state changes;
6. update abilities;
7. update auto-aim;
8. update player movement with collision;
9. resolve facing and locomotion animation;
10. update active weapon and spawn projectiles/fire events;
11. update secondary weapon (Dual Wield);
12. update projectiles, enemies, summons, pets, coins, boxes;
13. apply damage, death, room clear, pickups;
14. update camera interpolation state;
15. record interactive replay/test frames.

If something is "one frame late" or "moves while walking", look for state being
modified in `BuildRenderBatch()` or in the render-interpolation block instead of
`FixedUpdate()`.

## 7. Coordinate system

- World is Y-up.
- Sprite pixels-per-unit (PPU) is normally 16.
- Player collision is a 0.8x0.8 AABB (half extents 0.4) centered at foot+0.5.
- Camera is orthographic; default orthographic size is 10 world units.
- UI is logical 1920x1080 with a letterboxed viewport.
- Depth sorting uses `WorldDepthOrder(y, tie_break)`; higher y is farther back.
- Ground props use foot-based depth. Exceptions (beanbags, floor overlays) are
  explicitly marked `ground_depth: false`.

When a coordinate bug says `(x, y)`, the y is a world coordinate, not screen.
Teleport/review positions are chosen just south of the subject so the camera
centers it.

## 8. Collision architecture

`AabbCollisionWorld` stores axis-aligned boxes and one-way boxes. Movement is
axis-separated (X then Y) with clamping, which prevents tunneling for normal
player speeds but is not a full continuous sweep for every projectile.

Collision inputs:

- recovered floor edge solids;
- wall tilemap cells converted to 1x1 boxes;
- room door barriers while closed;
- obstacle variant cells;
- furniture/footprint boxes (forge tables, object-portal tables, bottles);
- selected static prefab colliders (bookshelves, display cases, etc.).

The scene builder deliberately skips giant `CompositeCollider2D` outlines; it
uses tile cells and recovered small colliders instead. If a room becomes
unwalkable, inspect the builder’s collider filters before removing collision
wholesale.

## 9. Rendering architecture

`VulkanRenderer` owns instance/device/swapchain/pipeline. `SpriteBatch` collects
`SpriteDraw` commands for the frame. `Application::BuildRenderBatch()` emits:

1. scene sprites (floor/wall/props/characters/doors);
2. player shadow/body/weapon (via `WeaponRenderer`);
3. pets/summons/projectiles;
4. item world (chests/coins);
5. interaction markers/pickup labels;
6. world-space stations (mech overlay, trader pedestals);
7. `GameUI` HUD/screens on top.

`SpriteDraw` includes position, size, UV, color, sorting layer, sorting order,
texture ID, pivot, rotation, flip flags. The renderer does not know game
semantics; it draws the batch.

## 10. UI architecture

`GameUI` is a data-driven state machine. `Application` builds `GameUIData` from
live systems every frame and calls `GameUI::Draw(ui_renderer_, data)`.
`UIRenderer` draws rectangles, text, nine-sliced panels, and scene sprites in
logical coordinates. `UIAssets` holds recovered UI atlas sprites and the font.

Screens:

```text
Gameplay, Pause, Settings, MainMenu, CharacterSelect,
WeaponSelect, SaveLoad, Trader, PetSelect, Workshop, MaterialChest
```

Actions are `UIAction` values; `Application::ProcessUIAction()` is the single
place where a UI action mutates game state. If a button works visually but does
nothing, check that its pointer hit-test uses the same rect helper as its draw
and that the action is handled in `ProcessUIAction`.

## 11. Asset environment

`AssetEnvironment` resolves the asset root. Runtime scenes are loaded from the
asset root’s `scenes/` directory. The current canonical build copies assets to
`build/assets/`. The log prints the resolved paths at startup.

There are three common roots:

- `build/assets/` — fresh runtime copy used by tests and the executable.
- `assets/generated/` — generated source pixels/scenes from the builder.
- `analysis/assets/` — committed metadata/scene JSON and manifests.

If the runtime and analysis scene disagree, you are looking at a stale copy.

## 12. Save architecture

`SaveData` is a native JSON schema, not the original Unity save. It is versioned
(`kCurrentVersion = 5`). `SaveSerializer` writes/reads JSON; `SaveManager` owns
the slot path and atomic file replacement. Save data includes:

- scene/campaign position, character, weapons, health/energy/coins/orbs;
- cleared rooms, chest-spawned rooms, chest/coin state;
- materials, unlocked blueprints, trader stock seed, sold trader offers;
- plants, seeds, pets, statue/mercenary/mount, potion state;
- map seed, aim mode, reduced weapon effects, UI suggestions.

`Application::SaveGameToDisk()` snapshots live systems into `SaveData`.
`LoadGameFromDisk()` restores and then reconfigures runtime systems. If you add
persistent state, add it to all three: `SaveData`, serializer write, serializer
read, plus save/load tests.

## 13. Dungeon/world flow

The hub is a scene with `is_hub = true`. Entering the dungeon portal calls
`SwitchRoom("hub_door")` or `ActivateRoom` on the world graph. `RoomManager`
holds room nodes and links generated from recovered metadata plus the map seed.
`BiomeSystem` selects level themes and enemy pools. `SwitchRoom`:

1. captures current room state (enemies, pickups, chests);
2. loads the target `SceneAsset`;
3. restores or creates room state;
4. positions the player at the matching door entrance;
5. rebuilds collision and surfaces;
6. configures items/weapons/UI;
7. starts room activation.

Room activation drives `Inactive -> Entered -> Combat -> Cleared`. Doors close
when combat begins and open when cleared.

## 14. Hub flow

`scene.is_hub` changes several behaviors:

- player spawn and camera bounds;
- garden plot configuration;
- NPC markers/dialogue;
- trader/forge/weapon station/material chest/mech interactions;
- hub chest runtime spawn;
- no dungeon room activation;
- main menu/return-home behavior.

The hub scene is generated by `tools/asset/build_hub_scene.py` from the recovered
HeroRoom level. It is the most coordinate-sensitive scene in the project.

## 15. Where to look first

| Symptom | First files |
|---------|-------------|
| Player movement/collision | `src/engine/locomotion`, `AabbCollision.cpp`, `Application::FixedUpdate` |
| Weapon position/recoil/muzzle | `WeaponRenderer.cpp`, `tests/unit/weapon_presentation_test.cpp` |
| Wrong sprite/prefab | `tools/asset/build_hub_scene.py`, `analysis/assets/scenes/hero_room.json` |
| Wrong interaction | `Application::TryInteract`, scene `interaction_markers` |
| Wrong UI rect/text | `GameUI.cpp`, `HudLayout`, `UIRenderer` |
| Missing/duplicate items | `ItemWorld.cpp`, `ItemAssets`, `Application::ConfigureRoomItems` |
| Save data lost | `SaveData.hpp`, `SaveSerializer.cpp`, `SaveManager` |
| Dungeon transition | `Application::SwitchRoom/ActivateRoom`, `RoomManager`, `RoomDoorController` |
| Trader stock | `Application::ConfigureTraderOffers`, `weapon_catalogue_`, item drop tables |
| Workshop blueprints | `game/hub/Workshop.*`, `GameUI::DrawWorkshop`, `ProcessUIAction` |
